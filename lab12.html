2 Supabase คืออะไร W12★★

Supabase คือแพลตฟอร์ม Backend-as-a-Service (BaaS) แบบ open-source ที่พัฒนาบนระบบจัดการฐานข้อมูล PostgreSQL ออกแบบมาเพื่อช่วยให้นักพัฒนาสร้างระบบหลังบ้าน (Backend) ได้อย่างรวดเร็ว โดยไม่ต้องเขียนโค้ดโครงสร้างพื้นฐานเองทั้งหมด

🏠 เปรียบเทียบง่าย ๆ
BaaS คือ “หลังบ้านสำเร็จรูป” แทนที่จะต้องตั้ง server, เขียน API, ทำระบบ login และที่เก็บไฟล์เอง Supabase เตรียมไว้ให้ เราแค่ออกแบบตารางแล้วเรียกใช้

ข้อดีของ Supabase (5 ข้อ) ★

ข้อดีรายละเอียด
1. Relational databaseใช้ PostgreSQL เต็มรูปแบบ (SQL) รองรับข้อมูลที่มีความสัมพันธ์ซับซ้อน และยืดหยุ่นกว่าฐานข้อมูลแบบ NoSQL
2. ลดเวลาเขียนโค้ด APIระบบสร้าง REST และ GraphQL API ให้อัตโนมัติทันทีตามโครงสร้างฐานข้อมูล (Database Schema) ที่ออกแบบไว้
3. ไม่มี Vendor Lock-inเป็น open-source และใช้ฐานข้อมูลมาตรฐาน จึงติดตั้งเองได้ (Self-host) หรือย้ายไป cloud อื่นได้ง่าย
4. ความปลอดภัยระดับแถวควบคุมสิทธิ์การเข้าถึงข้อมูลอย่างละเอียดผ่าน Row-Level Security (RLS) ของ PostgreSQL
5. รองรับงานด้าน AIมีส่วนขยาย pgvector สำหรับเก็บและค้นหาข้อมูล Vector ใช้กับระบบ AI และ RAG (Retrieval-Augmented Generation)

ฟีเจอร์หลัก

Storageจัดเก็บไฟล์สื่อและเอกสาร รองรับไฟล์ขนาดใหญ่

Row-Level Security (RLS) คืออะไร ★

RLS คือฟีเจอร์ของ PostgreSQL ที่ควบคุมสิทธิ์การเข้าถึงข้อมูลระดับแถว (Row) โดยกำหนด Policy ว่าผู้ใช้แต่ละประเภททำ SELECT, INSERT, UPDATE, DELETE กับแถวใดได้บ้าง เช่น ผู้ใช้เห็นเฉพาะข้อมูลของตัวเอง ส่วนผู้ดูแลระบบเห็นทั้งหมด

ใน Lab: ปิด RLS

เพราะยังไม่มีระบบ Authentication และข้อมูลเป็นข้อมูลจำลอง จึงปิดเพื่อให้ฝึกเชื่อมต่อและ query ได้ง่าย

ระบบจริง (Production)

ถ้ามีผู้ใช้หลายประเภทหรือข้อมูลที่ต้องควบคุมสิทธิ์ ควรเปิด RLS และกำหนด Policy ให้เหมาะสม

🔑 Primary key สำคัญอย่างไร
ticket_id / query_id เป็นค่าไม่ซ้ำที่ระบุแต่ละแถว ใช้เรียงข้อมูลให้คงที่ตอนทำ pagination และใช้เป็น conflict key ของ upsert() ใน Part 2 ส่วน created_at ต้องเป็น timestamp จึงจะกรองช่วงวันที่ด้วย gte/lt ได้ถูกต้อง

8 Section 2: run_query() แบบ reusable + cache W12★★★

จาก Query 5 เราเปลี่ยนค่าที่เคย hard-code (2026-01-01, 2026-02-01, Network) ให้กลายเป็น function arguments เพื่อให้รับค่าจาก UI ได้

ทำไมต้อง end_date + 1 วัน แล้วใช้ < ★

วันที่จาก st.date_input ไม่มีส่วนเวลา แต่ created_at มีทั้งวันและเวลา ถ้าใช้ created_at <= end_date ขอบเขตจะเป็น 00:00:00 ของ End date ทำให้ ticket ที่เกิดระหว่างวันนั้นถูกตัดออก

ผิด

created_at <= 2026-01-31 00:00:00

ticket 31 ม.ค. 09:00 หายไป

ถูก

created_at >= 2026-01-01 00:00:00
created_at < 2026-02-01 00:00:00

รวมทุกเวลาของวันสุดท้าย แต่ไม่รวมวันถัดไป

11 Part 2: ทำไมต้อง Preprocess และลบ Boilerplate W12ส่วนเสริม (Lab)

เป้าหมายของ model คือ ทำนาย category จาก technical problem ใน ticket เช่น “cannot connect to Wi-Fi” หรือ “printer is not detected” แต่ ticket บางรายการมีข้อความที่เป็นแค่รูปแบบการเขียน message เช่น greeting, closing หรือ signature

⚠ ปัญหา Shortcut signal
model ใช้ TF-IDF ซึ่งเรียนจากคำและคู่คำ มันไม่รู้ว่า phrase ไหนเป็นแค่รูปแบบการเขียน ถ้า boilerplate บังเอิญพบในบาง category บ่อยกว่า category อื่น model อาจจำ phrase นั้นเป็น shortcut signal แทนที่จะเรียนจากปัญหาจริง
★ ประโยคสำคัญ
Preprocessing ไม่ได้ทำให้ model performance ดีขึ้นโดยอัตโนมัติ การลบข้อมูลอาจลด noise แต่ก็อาจลบ information ที่มีประโยชน์ไปด้วย จึงต้องเก็บ raw data เป็น baseline แล้วทดลองเทียบจริงใน Part 3
ลองเล่น ลบ Boilerplate ด้วย regex เดียวกับ Lab

คำถาม: Preprocessing ช่วยให้ model ดีขึ้นจริงไหม? ต้องทดลองแบบ controlled คือ model ทั้งสองใช้ settings เดียวกัน (NGRAM_RANGE=(1, 2), REGULARIZATION_C=1.0) และ validation data ชุดเดียวกัน โดยเปลี่ยนแค่ training data (raw vs processed)

Metricคำถามที่ metric ช่วยตอบ
Accuracyจาก validation queries ทั้งหมด model ตอบถูกกี่ส่วน
Macro Precisionเมื่อ model ทำนายแต่ละ category คำตอบนั้นแม่นแค่ไหน (ให้น้ำหนักทุก category เท่ากัน)
Macro Recallในแต่ละ category จริง model หาตัวอย่างของ category นั้นเจอได้มากเท่าไร
Macro F1สมดุลระหว่าง precision กับ recall ของแต่ละ category แล้วเฉลี่ยทุก category

preprocessing อาจช่วยบาง category แต่ทำให้อีก category แย่ลง metrics จึงไม่จำเป็นต้องเปลี่ยนไปทิศทางเดียวกัน ต้องดู scores by category และ predictions ที่เปลี่ยน ประกอบ (validation set มีจำนวนเท่ากันทุก category: accuracy กับ macro recall จึงมักเท่ากัน)

15 Wrap-up W12

  1. Supabase = BaaS open-source บน PostgreSQL ที่มี Data API อัตโนมัติ, RLS, Auth, Storage, Realtime, Edge Functions, pgvector
  2. เชื่อมต่อด้วย publishable key + URL ใน secrets.toml และ GRANT ... TO anon (ห้ามใช้ secret/service-role key)
  3. Client → cache_resource ส่วน ผล query → cache_data(ttl=600) และ Refresh ด้วย .clear() + st.rerun()
  4. Filter, sort, limit ที่ database และระวังวันสุดท้ายด้วย < end_date + 1 day
  5. ข้อมูลเยอะใช้ pagination (.range) และเขียนกลับด้วย upsert(on_conflict=...) เฉพาะตอนกดปุ่ม
  6. preprocessing ไม่ได้ดีขึ้นเสมอ ต้องทดลองแบบ controlled และระวังการสรุปเหตุ
