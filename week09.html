2 จาก Script สู่ Web App: python vs streamlit run W9

คำสั่ง Python ปกติ

python main.py

เป็น Python process ธรรมดา ที่รันจบแล้วปิดตัว output แสดงใน terminal และ input ก็รับจาก terminal

คำสั่ง Streamlit

streamlit run main.py

ใช้ Python ecosystem เดิม แต่เปลี่ยน application model: Streamlit สร้าง web application ที่ทำงานต่อเนื่อง (long-lived server) คอยรอผู้ใช้โต้ตอบ

เกิดอะไรขึ้นบ้างหลังพิมพ์ streamlit run main.py ★

  1. Terminal command: เราสั่ง streamlit run main.py
  2. Server starts: Streamlit เปิด server process ขึ้นมา
  3. main.py runs on server: server รัน main.py แปลคำสั่ง st.* แต่ละคำสั่งให้เป็น interface element แล้วเปิดให้ browser เข้าถึง
  4. Browser renders UI: browser เปิดหน้าเว็บและแสดง title, widget, ตาราง, chart ฯลฯ ตามที่สคริปต์อธิบายไว้
💡 สาระสำคัญ
Browser ได้รับแค่ User interface ส่วน Python ยังอยู่ฝั่ง server เสมอ และ server นี้เป็นแบบ long-lived คือรอรับการโต้ตอบ และพร้อมรันสคริปต์ซ้ำได้ทุกเมื่อ

3 สถาปัตยกรรม Client–Server W9★

หลักใหญ่: Python runs on the server — not in the browser

ฝั่งหน้าที่
Browser / Clientแสดง widget และ output, รับ action จากผู้ใช้, แสดงผลที่อัปเดต
Streamlit Server (Python backend)โหลดข้อมูล, เรียกฟังก์ชัน, คำนวณ, เรียก model, เข้าถึง storage ของ server และมักเป็นฝั่งที่เรียก external API
การเชื่อมต่อสื่อสารสองทางแบบต่อเนื่อง (persistent two-way communication) ผ่าน WebSocket

ทำไมเรื่องนี้สำคัญ? กระทบ 4 ด้าน ★

🔒 SecuritySecret API key ต้องไม่ถูกส่งไปเป็นโค้ดฝั่ง browser ให้เก็บและใช้งานบน server เท่านั้น (Lab 12–13 ใช้ st.secrets)
⚡ PerformanceModel ขนาดใหญ่ใช้ memory และ compute ของเครื่องที่รัน server ไม่ใช่เครื่องของผู้ใช้
📁 FilesFile path ใน Python หมายถึง file system ของ server ไม่ใช่เครื่องของผู้ใช้
🐞 Debuggingerror ของ Python จะเกิดขึ้นที่ server (ดูใน terminal ที่รัน) ส่วน browser แค่แสดงผล

Local vs Deployed

Local development

เครื่องเดียว แต่ยังมี 2 บทบาท คือ Streamlit server และ browser client อยู่บนเครื่องเดียวกัน

จึง “ซ่อน” เส้นแบ่ง client–server ไว้ ทำให้เราลืมได้ง่ายว่า path หรือ memory เป็นของ server

Deployment

คนละเครื่อง เชื่อมกันผ่าน network โดย Cloud/host เป็น server (มี Python, data, model) และเครื่องผู้ใช้เป็น browser

path อย่าง C:/Users/... จะไม่มีอยู่บน cloud server

Server ownership: path และการคำนวณเป็นของ server

🛠 Pattern จาก Lab 09: ผูก path กับโฟลเดอร์ของ main.py

สไลด์บอกว่า “Anchor the data/ path to the folder that contains main.py” โดยใช้โค้ดนี้

วิธีนี้น่าเชื่อถือกว่าการเขียน "data/sample.csv" เฉย ๆ เพราะไม่ขึ้นกับ working directory ของ terminal ไม่ว่าจะรันจากโฟลเดอร์ไหน (หรือรันบน cloud) ก็หาไฟล์เจอเสมอ

4 Communication & Sessions: 1 แท็บ = 1 session W9

browser กับ server คุยกันผ่าน WebSocket ที่เปิดค้างไว้ (persistent) ซึ่งใช้ส่งทั้งการโต้ตอบและ output ที่อัปเดต

A · Browser → Serverค่า widget ที่เปลี่ยน และค่าที่ submit จะถูกส่งไปให้ Python
B · Server → Browserelement ใหม่และผลลัพธ์จะถูกส่งกลับมาอัปเดตหน้าเว็บ
C · แท็บใหม่ = session ใหม่แต่ละแท็บหรือหน้าต่างมี connection และ session context ของตัวเอง
💡 สาระสำคัญ
  • เปิด browser 1 แท็บ = สร้าง 1 session context
  • ถ้าเปิดแอปเดิมในแท็บที่สอง จะมี 2 connections และ 2 sessions
  • Server application ใช้ร่วมกัน แต่แต่ละแท็บมี ค่า widget และประวัติการโต้ตอบแยกกัน (เรื่องนี้จะต่อยอดเป็น Session State ใน Week 11)

8 Displaying Data: แสดงข้อมูล vs แก้ไขข้อมูล W9★

สไลด์เน้นว่า “การแสดงข้อมูล” กับ “การแก้ไขข้อมูล” เป็นงานคนละแบบ

Present data · เป้าหมาย: ตรวจดู ค้นหา เรียง สรุป
  • st.dataframe(df): ตาราง interactive ที่เลื่อน ปรับขนาด เรียงลำดับ และค้นหาได้
  • st.table(df.head()): ตาราง static ที่แสดงทุกแถวตรง ๆ เหมาะกับตารางเล็กหรือตารางสรุป
  • st.write(df): ให้ Streamlit เลือกวิธีแสดงเอง (automatic display)
Collect changes / KPIs · เป้าหมาย: รับ input หรือสื่อผลลัพธ์
  • st.data_editor(df): ให้ผู้ใช้แก้ตารางได้ และคืน DataFrame ที่ถูกแก้แล้วออกมา
  • st.metric(...): เน้นตัวเลขสำคัญ (KPI) พร้อม delta
⚠ Edits are not automatically saved to CSV. สิ่งที่แก้ใน data_editor ไม่ได้เขียนกลับไฟล์ ถ้าอยากบันทึกต้องเขียนลงไฟล์หรือ database เอง
