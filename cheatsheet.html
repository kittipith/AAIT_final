Week 9 · Streamlit Fundamentals

  • Streamlit = เปลี่ยน Python script → interactive web app โดยไม่ต้องเขียน frontend (HTML/CSS/JS) แยก
  • python main.py = process ธรรมดา ส่วน streamlit run main.py = เปิด long-lived server ที่รอการโต้ตอบ
  • ลำดับ: command → server starts → main.py runs on server (แปล st.* เป็น UI) → browser renders UI
  • Python runs on the server, not in the browser ซึ่งกระทบ 4 ด้าน: security (secret key), performance (model memory), files (path = file system ของ server) และ debugging
  • Local = เครื่องเดียวแต่ยังมี 2 บทบาท ส่วน Deployed = คนละเครื่องเชื่อมผ่าน network ถ้าต้องการไฟล์ของผู้ใช้ให้รับผ่าน file_uploader
  • Browser ↔ server คุยผ่าน WebSocket แบบ persistent โดย 1 แท็บ = 1 session และ server app ใช้ร่วมกัน แต่ค่า widget แยกกัน
  • Rerun: เปลี่ยน widget (นอก form) → ส่งค่า → script รันบนลงล่างทั้งไฟล์ → แสดงผลใหม่
  • Consequence 1: งานหนักถูกทำซ้ำ → Caching (W10) · Consequence 2: ตัวแปรธรรมดาหาย → Session State (W11)
  • st.dataframe interactive · st.table static · st.write auto · st.data_editor คืน DataFrame ที่แก้แล้ว (ไม่ save ลง CSV) · st.metric KPI + delta
  • Widget return = Python value ธรรมดา โดย button True เฉพาะรอบที่กด, multiselect คืน list, slider คืนตัวเลขหรือ tuple
  • เลือกไม่ครบให้ใช้ st.warning (ไม่ใช่ error) และตั้ง label ดี ๆ จะได้ไม่ต้องอธิบายเยอะ
  • Form: ค่าถูกเก็บแล้วส่งพร้อมกันเมื่อกด form_submit_button (ต้องมีเสมอ) ระหว่างกรอกจึงไม่ rerun
  • Layout: Sidebar = global controls · Columns = metrics เคียงกัน · Tabs = มุมมอง · Expander = รายละเอียด · Container = จัดกลุ่ม
  • Dashboard rhythm: controls → key metrics → main views → optional details

Week 10 · Caching

  • Cache งานที่ แพง + เสถียรพอจะใช้ซ้ำข้าม rerun เช่น อ่านไฟล์ใหญ่, เรียก API/DB, โหลด model/tokenizer/embeddings
  • HIT = มี entry ที่ตรงกันและยังใช้ได้ จึงคืนค่าเดิมโดยไม่รัน function body · MISS = รัน function แล้วเก็บผล
  • Cache ข้ามแค่ function body ไม่ได้ข้าม rerun ส่วนอื่นของ script ยังรันบนลงล่างตามปกติ
  • Cache identity = ฟังก์ชันเดิม + arguments เดิม + source code เดิม ถ้าเปลี่ยนอย่างใดอย่างหนึ่งจะ MISS และสร้าง entry ใหม่ (1 ฟังก์ชันมีได้หลาย entry)
  • @st.cache_data ใช้กับ data (DataFrame, list, dict, str, ผลจาก API) โดย serialize เก็บไว้แล้วคืนสำเนา (copy) ให้ผู้เรียกแต่ละคน
  • @st.cache_resource ใช้กับ shared resource (ML model, DB connection) โดยคืน object ตัวเดียวกัน ไม่ copy จึงต้อง thread-safe และห้าม mutate
  • ถ้า mutate object จาก cache_resource ทุก session จะเห็นการเปลี่ยนแปลง เช่น ตัวอย่าง remove(1) ที่ทำให้รอบถัดไปเกิด ValueError
  • Arguments ต้อง hashable (Lab แปลง list เป็น tuple) ถ้าใส่ _ นำหน้า parameter (เช่น _db_connection) Streamlit จะไม่นำมาคิด cache key
  • ttl=3600 (หรือ timedelta) ใช้กันข้อมูล stale · max_entries=1000 จำกัดจำนวน entry (ลบอันเก่าสุดออก) ไม่ได้จำกัดขนาด byte
  • show_spinner=False หรือข้อความเอง และ Lab ใช้ show_time=True แสดงเวลาที่ใช้
  • เคลียร์: func.clear() (ฟังก์ชันเดียว) · st.cache_data.clear() / st.cache_resource.clear() (ทั้งประเภท)
  • Version the input: ส่ง os.path.getmtime(path) เป็น argument พอไฟล์เปลี่ยน key ก็เปลี่ยน แล้ว refresh เอง
  • คำถามก่อนตัดสินใจ cache: ใช้ซ้ำแล้วประหยัดงานจริงไหม? และ ใช้ซ้ำแล้วยังถูกต้องไหม? (SKIP: งานเล็ก, input ไม่ซ้ำ, state ของผู้ใช้, side effect)

Week 11 · Session State

  • Session = การเชื่อมต่อระหว่าง 1 แท็บ กับแอป และ st.session_state เก็บ key–value ที่อยู่รอดข้าม rerun ภายใน session นั้น
  • Session State = “my current workflow” (ของ session เดียว, หายเมื่อ session จบ) · Cache = “expensive work we can reuse” (แชร์ทุก session)
  • Init pattern: if "count" not in st.session_state: st.session_state.count = 0 เพื่อไม่ให้ reset ทุก rerun
  • ใช้ได้ทั้ง st.session_state["k"] และ st.session_state.k ลบด้วย del st.session_state["k"] ถ้าจะลบทุก key ให้วน list(st.session_state.keys())
  • Widget ที่มี key="name" จะเขียนค่าลง st.session_state["name"] อัตโนมัติ (key ต้องไม่ซ้ำ)
  • ถ้าจะตั้งค่าเริ่มต้นให้ keyed widget ให้ set state ก่อนสร้าง widget ถ้า set หลังจะเกิด StreamlitAPIException
  • Callback: ผู้ใช้เปลี่ยน widget → callback รันก่อน → state update → script rerun
  • on_click=f คือส่งฟังก์ชัน (ถูก) ส่วน on_click=f() คือเรียกทันทีทุก rerun (ผิด)
  • on_change ใช้กับ input widget และส่งค่าคงที่ด้วย args/kwargs ได้ ถ้าเป็น form ให้ใส่ callback ที่ submit button
  • Common errors: (1) อ่าน key ก่อน init (2) แก้ค่า widget หลังสร้าง (3) ตั้ง default ซ้อนสองที่ (state + value=)
  • Button state ephemeral: ห้ามบังคับ state ของปุ่ม ให้เก็บผลลัพธ์แทน เช่น submitted = True
  • State หายเมื่อเปิดแท็บใหม่ / reload / connection reset จึงเป็น temporary memory ไม่ใช่ database
  • ถามตัวเอง: ใครควรเห็น? (session เดียว → state, ทุกคน → cache/storage) และ อยู่นานแค่ไหน? (ถึงปิดแท็บ → state, ข้ามการเข้าใช้ → file/DB)

Week 12 · Lab 12 Database (Supabase)

  • Supabase = open-source Backend-as-a-Service (BaaS) บน PostgreSQL
  • ข้อดี: Relational/SQL · สร้าง REST + GraphQL API อัตโนมัติจาก schema · ไม่มี vendor lock-in (self-host ได้) · RLS · pgvector (vector search สำหรับ AI/RAG)
  • ฟีเจอร์: Database · Authentication (email/password, OAuth) · Storage · Realtime (WebSockets) · Edge Functions (serverless)
  • RLS (Row-Level Security) = ควบคุมสิทธิ์ระดับแถวด้วย policy (SELECT/INSERT/UPDATE/DELETE) ใน Lab ปิดไว้เพราะเป็นข้อมูลจำลองและไม่มี auth แต่ระบบจริงควรเปิด
  • Primary key: ticket_id (tickets), query_id (validation) และ created_at เป็น timestamp
  • ใช้ Publishable key (sb_publishable_…) เท่านั้น ห้ามใช้ Secret / Service Role key (sb_secret_…) เพราะมีสิทธิ์สูงและข้าม RLS ได้
  • เก็บ supabase_url + supabase_key ใน .streamlit/secrets.toml แล้วอ่านด้วย st.secrets["..."]
  • GRANT SELECT ON TABLE public.helpdesk_tickets, public.helpdesk_validation TO anon; ให้ role anon อ่านได้
  • Client: @st.cache_resource + create_client(url, key) สร้างครั้งเดียวแล้วใช้ซ้ำ
  • Query chain: .table() → .select() → filter(.eq/.gte/.lt) → .order() → .limit() → .execute() แล้วต่อด้วย pd.json_normalize(response.data)
  • Filter ที่ database ไม่ใช่โหลดทั้งตารางมา filter ด้วย pandas และรวมทั้งวันสุดท้ายด้วย .lt("created_at", end_date + 1 day)
  • Query ใช้ @st.cache_data(ttl=600) ปุ่ม Refresh เรียก func.clear() + st.rerun() และไม่ clear client
  • Data API จำกัดจำนวน row ต่อ request จึงใช้ pagination .range(start, start+999) วนจนได้ batch ที่น้อยกว่า page_size
  • upsert(on_conflict="ticket_id") = ถ้ายังไม่มีให้ insert ถ้ามีแล้วให้ update จึงไม่เกิดแถวซ้ำ (เขียน DB เฉพาะเมื่อกดปุ่ม)

Week 13 · Lab 13 Deployment

  • Pipeline: Local app → GitHub repository → Streamlit Community Cloud → Public URL → Users
  • ต้องมี: GitHub account, share.streamlit.io account, แอปที่รัน local ได้, requirements.txt และ (ถ้าใช้ DB) secrets
  • requirements.txt ใส่เฉพาะ external libraries (streamlit, pandas, scikit-learn, supabase) ส่วน standard library (datetime, json, re, pathlib…) ไม่ต้องใส่
  • ดูเวอร์ชันด้วย pip show streamlit และ pin เช่น streamlit<=1.50.0 เพื่อกันพฤติกรรมต่างจาก local เมื่อ library อัปเดต
  • แอปอ่าน data/ ดังนั้นต้อง upload CSV ขึ้น GitHub ด้วย และทดสอบ local ก่อนด้วย python -m pip install -r requirements.txt + python -m streamlit run main.py
  • Deploy: Create app → Deploy a public app from GitHub → repo, branch (main), entry point (main.py), App URL, Advanced settings (Python version, Secrets)
  • ห้าม commit/upload .streamlit/secrets.toml ให้ไปวางค่าใน Advanced settings → Secrets แทน
  • แนวคิด: source code เดิม เปลี่ยนแค่ที่เก็บ configuration (local secrets.toml → Cloud Secrets) และโค้ดยังอ่าน st.secrets เหมือนเดิม
  • เปิดหน้าเว็บได้ ≠ deploy สำเร็จ ถ้าต่อ DB ไม่ได้หรือ workflow หลักพัง ก็ยังถือว่าไม่สมบูรณ์
